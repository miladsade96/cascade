# Cascade 1.9.0

Release 1.9.0 adds cluster-gated Kafka transaction protocol V2 while preserving transaction V1 during mixed-version rolling upgrades.

## What changed

- The cluster exchanges and unanimously finalizes `transaction.version=2` before clients can select V2 semantics.
- Produce v12 implicitly enrolls transaction partitions and TxnOffsetCommit v5 implicitly enrolls consumer groups.
- EndTxn v5 commits the outcome and next producer identity atomically, returns the bumped identity, and gives retries the same stored result.
- Epoch exhaustion rotates the producer ID; timeout and producer reinitialization preserve the same durable fencing outcome.
- Delivery images store the active protocol and resulting completion identity in a versioned format while continuing to read headerless legacy images.
- Flexible request/response framing, unknown tagged fields, protocol-mixing rejection, restart recovery, coordinator failover, and the replicated-append publication race have dedicated regression coverage.
- Source, deployment manifests, compatibility metadata, and container defaults now agree on version 1.9.0.

## Qualification

On 2026-10-16, Eclipse Adoptium Java 21.0.11 passed the clean Scala and Kafka-Java release gate: **612/612 tests**, **0 failures**, and **0 errors** in **273 seconds**. The run includes 25 Kafka-client end-to-end cases and the three-broker transaction-coordinator failover path. The [transaction V2 qualification report](../performance/2026-10-16-transaction-v2.md) records focused counts, the cache-accounting defect found and fixed during the run, and the exact boundary.

The local release image tag is `miladsade96/cascade:1.9.0`. I keep local image creation and Docker Hub publication separate: this source qualification does not claim a registry push or a registry digest.

## Remaining production gates

This release is not yet a universal production-grade Kafka replacement. A broader client/version matrix, dedicated-host RF=3 transaction capacity, authenticated 72-hour multi-tenant soak evidence, arbitrary packet impairment, coordinated multi-host restore drills, compressed Snappy/LZ4/Zstd compaction rewriting, and physical power/device-loss qualification remain open.
