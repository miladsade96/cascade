# Cascade 1.8.0

Release 1.8.0 turns the existing distributed-systems implementation into evidence that can be understood, inspected, and reproduced without weakening the production-readiness boundary.

## What changed

- The README now presents the protocol, storage, delivery, replication, coordination, security, operations, and evidence before deep implementation detail.
- GitHub-rendered diagrams document the internal request path and three-node replication/failover sequence.
- Kafka request dispatch uses Produce, Fetch, Metadata, Group, Transaction, Admin, and Security domains.
- Membership projection, controller timing/lease policy, coordinator routing, and partition-leadership transitions are independent tested components behind `ClusterManager`.
- Eight ADRs record context, decisions, rejected alternatives, trade-offs, and consequences.
- A real-container demo kills the discovered RF=3 partition leader and verifies exact acknowledged records.
- A same-client comparison harness records Cascade and Apache Kafka with identical workload and container limits.
- Internal peer endpoints can now differ from client-advertised cluster endpoints, which makes NAT and independent-container failover topologies practical.
- The compatibility matrix distinguishes external evidence from capabilities not exercised by a client smoke test.

## Compatibility

The public Kafka API/version range, metadata format 12, internal peer API range, storage formats, and distributed-quota feature levels are unchanged from 1.7.0. The new `--advertised-cluster-nodes` option changes deployment configuration, not the wire or storage format.
