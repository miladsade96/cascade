# Cascade 1.14.0

Release 1.14.0 adds a controller-coordinated, all-voter snapshot generation with one portable global manifest and safe verified retention.

## What changed

- The active controller prepares every stable voter behind a leased request barrier and captures node artifacts concurrently.
- Snapshot identity fences controller ID and term, metadata version, and the exact metadata SHA-256 before and after each capture and before publication.
- Every artifact is bound to its node ID and durable directory ID and includes its local backup-manifest checksum, file count, byte count, and exact partition high watermarks.
- The controller requires every voter, rejects unavailable or joint membership, and requires equal high watermarks across every ISR before atomically publishing `cascade-cluster-snapshot.manifest`.
- Prepare, capture, and release use bounded internal RPCs. Snapshot control uses a dedicated peer transport so blocked ordinary traffic cannot prevent barrier release.
- A lost release expires safely after its lease; a capture holds the lease until its forced copy finishes.
- `verify-cluster-snapshot` validates the global manifest and every exact local artifact. `prune-cluster-snapshots` deletes only verified generations with enough newer verified replacements and fails closed on any corrupt published generation.
- Partial captures never receive a global manifest and are not authoritative generations.

The operator workflow, collection layout, restore procedure, failure interpretation, and remaining external qualification are documented in [backup and restore](../backup-restore.md).

## Qualification

The focused Java 21 snapshot suite passed **45/45** manifest, barrier, internal-wire, feature-gating, participant-fencing, three-voter integration, fault, repository, command, quorum-codec, and backup-recovery tests. It verifies exact 50-record/high-watermark capture on every ISR, dropped prepare and capture calls, lease recovery, controller/metadata changes, directory identity, malformed frames, artifact tampering, fail-closed retention, and a successful generation after failure.

The Kafka-client end-to-end suite then passed **26/26** three times consecutively after its live compaction probe was made tolerant of a segment that is atomically retired between directory enumeration and read. The clean whole-software run passed **672/672** unit, integration, Kafka-client, security, storage, cluster, backup, fault, and end-to-end tests with zero failures or errors in **208 seconds** on 2026-10-21.

The local `miladsade96/cascade:1.14.0` Linux/amd64 image is built from the final release commit with SBOM and maximum provenance. Publication remains blocked until the exact image passes packaged runtime, five-language client/restart, and fail-closed zero-finding security gates. Docker Hub publication and registry digest recording are separate actions.

## Boundaries

This release closes the software-level coordinated snapshot and verified-retention milestone. It does not execute encrypted cross-site transfer, a recurring full-cluster restore drill, multi-terabyte restore timing, the authenticated 72-hour multi-tenant soak, dedicated-host RF=3/TLS capacity, physical power/device-loss qualification, arbitrary external packet impairment, or an adjacent published-image rolling campaign. I still do not describe Cascade as a universal production replacement for Apache Kafka.
