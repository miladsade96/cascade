# Cascade 1.15.0

Release 1.15.0 turns adjacent-release compatibility into an executable image gate and adds a reviewed Kafka Java client-version matrix.

## What changed

- The adjacent-image runner inspects and pins both tags to immutable image IDs before it creates any resources.
- A hardened three-broker Docker topology starts on the 1.14.0 image with RF=3, minimum ISR 2, synchronous flushing, persistent volumes, read-only roots, no Linux capabilities, and `no-new-privileges`.
- One idempotent producer remains alive while non-leaders are upgraded, one node is rolled back, the old leader is killed with records in flight, and the cluster completes the upgrade.
- The runner rejects missing retries, offset gaps, duplicate or reordered values, wrong committed offsets, broker protocol errors, failed rollback, failed compatible downgrade, and failed full-cluster restart recovery.
- Its atomic JSON report records the exact image IDs, release labels, Git revisions, phases, retry count, original leader, recovery result, and elapsed time.
- The Java compatibility gate independently tests Apache Kafka clients 3.9.1, 4.0.0, 4.1.1, 4.2.0, and 4.3.1 against the candidate image. Every version must create a topic, produce 25 exact idempotent records, consume them through a group, commit offset 25, and read that offset through Admin.
- The container workflow builds the image with a real OCI creation label, runs the Java matrix on every candidate, and can run the adjacent-image gate when an existing baseline image is supplied.

The procedure and downgrade boundary are documented in [rolling upgrades](../rolling-upgrades.md). The supported client ranges and matrix policy are documented in [compatibility](../compatibility.md).

## Qualification status

The new focused model, command-runner, topology, lifecycle, evidence, and exact-ledger tests pass on Java 21. The 1.14.0 image also passes the complete five-version Java client matrix with exact 25-record and committed-offset checks for every version.

The first whole-software run executed **687 tests** and exposed one time-dependent bearer-expiry test: its 10 ms credential could expire before the test's first assertion while the complete suite was under load. I replaced the wall-clock race with an injected clock and verified the corrected security suite **6/6**. A fresh full-suite run and the final 1.14.0-to-1.15.0 image campaign are required before I mark the release candidate qualified.

## Release gates

I build the final image from the final release commit, then require all of these gates against that exact revision:

```powershell
.\scripts\qualify-adjacent-images.ps1 `
  -BaselineImage miladsade96/cascade:1.14.0 `
  -BaselineVersion 1.14.0 `
  -CandidateImage miladsade96/cascade:1.15.0 `
  -CandidateVersion 1.15.0 `
  -Report artifacts/adjacent-images-1.14.0-to-1.15.0.json

.\scripts\qualify-java-client-versions.ps1 `
  -BrokerImage miladsade96/cascade:1.15.0 `
  -ExpectedVersion 1.15.0 `
  -Report artifacts/java-client-versions-1.15.0.json
```

The packaged runtime, five-language clients, security-gate regression tests, and authenticated zero-finding image scan remain mandatory. A build is not a Docker Hub publication, and a scanner authentication failure is not a security pass.

## Boundaries

This release qualifies one real adjacent image pair and five Java client releases. It does not prove every historic or future image combination, non-Java client version range, multi-architecture behavior, a 72-hour authenticated multi-tenant soak, dedicated-host RF=3/TLS capacity, arbitrary external packet impairment, cross-host restore timing, or physical power/device-loss safety. I do not describe Cascade as a universal production replacement for Apache Kafka while those operational gates remain open.
