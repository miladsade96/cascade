# Cascade 1.12.0

Release 1.12.0 keeps Kafka producer identity, epoch, sequence, duplicate detection, and transaction visibility valid when compaction or retention removes their original batches.

## What changed

- Every partition has an atomic, versioned, CRC32C-protected `producer-state.checkpoint` containing the last five accepted batches per producer.
- The checkpoint preserves base/last offsets, producer ID, epoch, base/last sequence, record count, timestamp, compression, and transaction/control flags.
- Snapshot, clean shutdown, compaction, and time/size retention force producer state before log files can change. Startup merges checkpoint state with surviving magic-v2 headers.
- Corrupt, oversized, unordered, or internally inconsistent checkpoints fail recovery instead of silently weakening idempotence.
- Authoritative replica truncation prunes producer metadata from the discarded suffix, and full replica reset clears it before replacement data arrives.
- Storage lifecycle receives a per-partition floor from the acknowledged delivery image. Active transactions and completed outcomes with unapplied offsets prevent time/size retention from erasing unresolved data.
- Compaction continues to preserve transactional and control batches byte-for-byte while ordinary keyed records remain eligible for all-codec rewriting.

The contract is documented in [delivery semantics](../delivery-semantics.md), the [idempotent producer ADR](../adr/0005-idempotent-producers.md), and the [producer-state recovery runbook](../producer-state-recovery.md).

## Qualification

On 2026-10-20 the final Java 21.0.11 whole-software run passed **634/634** unit, integration, Kafka-client, security, storage, cluster, fault, and end-to-end tests with zero failures or errors. sbt reported **164 seconds**. The Kafka-client end-to-end suite separately passed **26/26** after its compaction wait was made dependent on actual obsolete-batch removal rather than checkpoint creation alone.

Focused coverage proves:

- checkpoint round-trip, replacement, bounds, and checksum failure;
- producer identity/epoch/sequence recovery after compaction and size retention;
- duplicate retries returning their original offset after the source batch was cleaned and the broker restarted;
- contiguous sequence acceptance and gap rejection after restart;
- checkpoint pruning during authoritative replica truncation/reset;
- active and pending-outcome transaction retention floors;
- byte-exact transactional/control batches across compaction and restart; and
- real Kafka 4.3.1 `read_committed`/`read_uncommitted` visibility after compaction and restart.

I built `miladsade96/cascade:1.12.0` as a scratch, non-root `linux/amd64` image with SBOM and provenance. The packaged runtime passed **50/50** TLS, peer-security, record-batch, and partition-log tests plus PLAIN/SCRAM production and restart recovery. Java 4.3.1, KafkaJS 2.2.4, Python confluent-kafka 2.15.0, franz-go 1.21.0, and Confluent.Kafka .NET 2.15.0 each verified 25 exact records; Java verified them again after container restart. Docker Scout 1.26.0 reported **zero vulnerability findings** across 15 inventoried packages. Local evidence is under the ignored `artifacts/` tree.

## Boundaries

This release closes producer-state loss caused by local cleanup and prevents local retention from crossing unresolved transaction ranges. It does not make cleanup decisions cluster-wide, prove behavior under a physical power/device cut, or replace the required authenticated 72-hour multi-tenant soak and dedicated-host RF=3/TLS capacity campaigns. Docker Hub publication and registry digest recording remain separate from this local image build. I still do not describe Cascade as a universal production replacement for Apache Kafka.
