# Cascade 1.3.1

Status: locally qualified on 2026-09-04; publication pending. Target: `miladsade96/cascade:1.3.1`, Linux/amd64 only. The final candidate passes the zero-finding security gate without exceptions.

## Security changes

The post-publication scan of 1.3.0 found 21 vulnerabilities: one critical, three high, three medium, ten low, and four unspecified. Seven were attributed to `libssl3` and fourteen to `libc6`. The original scan failure was a release-process gap, not a clean result. The [1.3.0 notes](1.3.0.md) preserve the historical qualification and subsequent finding.

I replace the Debian/glibc/OpenSSL runtime with a scratch-based image containing a minimal Alpine 3.24/musl installation and a musl-native Temurin 21.0.12+8 runtime. The Dockerfile pins both JDK images, the Alpine image, and the installed runtime package versions. Only musl, C++ support libraries, certificates, timezone data and base configuration enter the final filesystem; no shell, package manager, glibc or OpenSSL is copied. The real APK database remains available to inventory scanners. Package signatures and HTTPS verification remain enabled.

I first evaluated Debian 13 without OpenSSL. Although its registry base scan reported zero findings, the complete application inventory scan reported seven low-severity, unfixed glibc findings. I rejected that candidate, retained its evidence locally, and kept zero findings mandatory rather than adding exceptions. The musl runtime removes that affected implementation. I require the [release security gate](../container-security.md) to scan the complete attached inventory, including the JDK and Scala jars. The gate rejects every severity, scanner errors, incomplete inventory, wrong image identities, and stale output-directory reuse. No CVE exceptions, severity filters, or base-package exclusions are configured.

Cascade continues to use Java TLS. Security-library tests run with the packaged JVM and broker jars; external Kafka clients run on a host JDK against the image's actual entry point. The first attempt to run Kafka clients inside the minimal broker JVM failed because the test clients require JMX modules. I separated the client and broker runtimes instead of adding client-only modules to the release. No broker protocol, storage format, or metadata feature level changes in this patch. Earlier glibc throughput measurements do not establish musl performance.

The release workflow builds once, tests the actual image, scans it, and passes the exact image archive to publication. Publication scans again and pushes that image without rebuilding. Only Linux/amd64 and the explicit version tag are published; ARM64 needs its own runtime qualification before re-enabling it. `1.3.0`, `latest`, and Git branches are not pushed or changed by this release operation.

I retain unsuccessful attempts as well. One full run overlapping the container campaigns passed 444/446 tests: a TLS trust-reload check timed out and a consumer-rebalance test reported one duplicate. Both suites subsequently passed the focused run, followed by the complete 446-test pass without competing workloads. This does not prove the earlier failures were caused by contention or establish reliability under sustained load; no broker-code fix was made for those failures. The failed run remains in `release-1.3.1-tests-final.log`. An earlier complete run also passed 446/446 (`release-1.3.1-tests.log`).

The first external secure-client attempt also exposed an invalid test-client timeout configuration. I set its request timeout below its API timeout, then reran the entire packaged-runtime security campaign successfully. APK installation initially rejected untrusted indexes in the empty runtime root; I fixed the build by copying signing keys from the pinned Alpine stage, without disabling signature or HTTPS checks.

The five-language campaign reused the previously qualified Linux Go smoke binary (SHA-256 `782d11023f30b70575fdeb2c9019fc40c447067fcc4bf61eb74399b5a85d8473`). The three-broker campaign used the documented local shared-network-namespace topology, not separate hosts or physical failure domains. Synthetic test containers and cluster volumes were removed; local logs, scan reports and image archives remain ignored release evidence, not committed artifacts. These are local results, not a claim that GitHub Actions ran remotely.
