# Cascade 1.11.0

Release 1.11.0 makes Kafka magic-v2 validation and compaction rewriting fail safely around the exact Kafka CRC32C contract.

## What changed

- Produce validates the complete batch envelope, magic, counters, compression identifier, and CRC32C before assigning a broker offset.
- The CRC covers byte offset 21 (`attributes`) through the declared end of the batch. Assigning `baseOffset` remains safe because that field is outside Kafka's CRC region.
- Invalid batches return Kafka `CORRUPT_MESSAGE` (code 2), consume no offset, and do not close an otherwise valid client connection.
- Recovery rebuilds indexes only from CRC-valid batches. It can truncate a damaged complete batch only at the final physical position of the final active segment; interior corruption fails startup without deleting evidence.
- Record decoding is bounded by the batch, decompressed payload, and individual record boundary. Offset deltas, header counts, timestamps, and variable-length integers are checked before compaction can use them.
- Every uncompressed, Gzip, Snappy, LZ4, or Zstd rewrite recalculates batch length, retained record count, and CRC32C, then validates and decodes the result again before atomic replacement.

The full behavior and incident boundary are in the [magic-v2 integrity contract](../record-batch-integrity.md) and [operations runbook](../operations.md#record-batch-corruption-response).

## Qualification

On 2026-10-20 I ran `sbt clean test` on Java 21.0.11. All **621/621** unit, integration, Kafka-client, security, storage, cluster, fault, and end-to-end tests passed with zero failures or errors. The measured wall time was **216.785 seconds**; sbt reported 213 seconds.

The focused coverage includes:

- corrupted Produce CRC rejection with a successful valid append on the same connection;
- proof that broker base-offset assignment does not change the stored CRC;
- active-tail CRC repair and interior-corruption evidence preservation;
- bounded record offset/length rejection;
- immutable header preservation and post-rewrite CRC verification;
- all five Kafka compression modes accepted by Cascade; and
- deployment/version alignment.

I also built a scratch, non-root `linux/amd64` candidate with SBOM and provenance attestations. Its packaged runtime passed **44/44** TLS, peer-security, record-batch, and partition-log tests. Real Kafka clients then verified 25 records each through Java 4.3.1, KafkaJS 2.2.4, Python confluent-kafka 2.15.0, franz-go 1.21.0, and Confluent.Kafka .NET 2.15.0; Java verified the same 25 records after container restart. The secure image gate produced and recovered 25 records for each of PLAIN, SCRAM-SHA-256, and SCRAM-SHA-512, and rejected all three invalid credentials.

Docker Scout 1.26.0 scanned the candidate's generated SPDX SBOM and returned **zero vulnerability findings** across 15 inventoried packages. Candidate evidence is local and ignored by Git under `artifacts/`; the final tag still needs its own immutable scan result before publication.

## Boundaries

This release detects wire and persisted batch corruption and prevents unsafe compaction rewrites. It does not prove that damaged data can be reconstructed locally. Recovery still depends on an authoritative in-sync replica or verified backup.

The local source, client, runtime, and scanner results are not a substitute for the remaining multi-day authenticated soak, dedicated-host RF=3/TLS capacity campaign, replicated cleanup coordination, published-image rolling qualification, coordinated cross-host snapshot lifecycle, or physical power/device-loss testing. I still do not describe Cascade as a universal production replacement for Apache Kafka.
