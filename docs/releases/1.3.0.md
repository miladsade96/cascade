# Cascade 1.3.0

Release image: `miladsade96/cascade:1.3.0`, Linux/amd64.

Status: **built, locally qualified, and published to Docker Hub on September 4, 2026**. I verified the remote index digest matches the tested local image, pulled it by immutable digest, and executed its Java runtime successfully. I pushed only `1.3.0`; older tags and `latest` were not changed.

## Included changes

- Format-11 immutable shard-object storage with atomic publication and conservative recovery/reclamation.
- Bounded offset batching with deadline/admission controls, rollback isolation, and fixed-label metrics.
- Content-validated coordinator snapshot caching, canonical offset views, and group-indexed offset fetches.
- Ownership-aware group expiry, session-preserving image installation, and safe wakeup of blocked group sync calls.
- Exact-offset failover/restart qualification, paired preparation benchmarks, and five-language client checks.

The [development qualification report](../performance/2026-09-04-coordinator-snapshots.md) records 445 passing full-suite tests, 79 Linux tests, exact one-million-record recovery, and three pinned source rolling campaigns. Those measurements describe 1.3.0-SNAPSHOT development; the final release image is qualified separately below.

## Deployment and compatibility

I align `VERSION`, `deploy/VERSION`, Docker labels, Node package metadata, Compose build defaults, and Kubernetes pins to 1.3.0. The [container guide](../containers.md) contains the run commands. The Dockerfile pins the JDK and distroless base by immutable index digest.

The storage feature activates only after every voter supports it. Once format 11 activates, rollback to an older incompatible binary is rejected; I preserve a verified pre-upgrade backup and follow the [rolling procedure](../rolling-upgrades.md). Source-based rolling tests do not qualify the published format-8 image predecessor. This release is not a production-grade Kafka replacement: shared consensus/service locks, broader compatibility, dedicated-host capacity, multi-day soak, and physical power/device-loss gates remain open.

I ran the image's own non-root user, JVM entry point and health probe with a read-only root filesystem and persistent data. The single-node runner used the inspected immutable image ID. The three-broker Compose campaign used the same unchanged local tag with `--no-build --pull never`, a unique project, and a loopback-only port override. Its three processes share a network namespace; this is not separate-host or network-failure qualification. I removed only that disposable cluster's containers, network, and synthetic-data volumes after the check. Single-node synthetic data and logs remain in ignored local artifacts.

The initial cluster attempt passed Java but rejected the KafkaJS test's replication-factor-1 write under the cluster's minimum-ISR-2 policy. I made the smoke test accept `CASCADE_REPLICATION_FACTOR=3`, retained the default of 1 for single-node checks, and reran the complete cluster campaign successfully. No broker durability setting was weakened.

The first two five-language attempts stopped at Go dependency acquisition because GitHub/DNS downloads failed in the broker's network namespace. I built the same pinned Go client on Docker's default network, without disabling TLS or `go.sum` verification, then ran that binary inside the broker's network namespace. The final campaign passed every language and restart check; no language was skipped.
