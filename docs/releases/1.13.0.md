# Cascade 1.13.0

Release 1.13.0 coordinates retention and compaction across every in-sync replica of a partition instead of allowing independent local cleanup decisions.

## What changed

- The partition leader calculates one deterministic delete boundary, compaction boundary, and tombstone cutoff under the Produce/recovery partition lock.
- Every current ISR member must validate and force the epoch-fenced plan before the leader commits or applies it.
- `replicated-cleanup.checkpoint` stores prepared, committed, and applied generations through atomic replacement with CRC32C validation.
- Prepared-only work never deletes data after restart. Committed work resumes idempotently, and a newer leader epoch supersedes an incomplete generation.
- Replica recovery transfers the committed cleanup state before ISR admission, including re-certification when leadership changed.
- The `replicated-cleanup=1` feature activates only after every voter supports it and the full-voter metadata commit completes.
- Lifecycle shutdown now drains before the replication executor closes, avoiding cleanup RPC submission during broker teardown.

The protocol, recovery behavior, rolling boundary, and operator response are documented in [replicated partition cleanup](../replicated-cleanup.md).

## Boundaries

This release closes the software-level replicated cleanup coordination milestone. It does not prove physical device behavior under sudden power loss, replace the required authenticated 72-hour multi-tenant soak, publish a dedicated-host RF=3/TLS capacity envelope, coordinate one snapshot artifact across replica hosts, or qualify an adjacent pair of published images. Docker Hub publication and registry digest recording remain separate from the local image build.
